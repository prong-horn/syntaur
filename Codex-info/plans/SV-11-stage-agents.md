## Decisions and behavior contract

### 1. Resolve one stage target

Add `src/ticket-templates/stage-dispatch.ts` with pure `resolveStageDispatch(manifest, stage, override?)` returning `{stage, role:'agent'|'reviewer', agentId, auto, instructions}` or null. Explicit override changes the target for this dispatch only, never template, assignee, default participant or model. It requests dispatch even if that stage has auto=false. A start override on a stage with no declared target uses role=agent. Unknown override ids must be exact lookup failures: do not call resolveAgent in a way that falls back to the default definition.

Reject manifests declaring both nonempty agent and reviewer on one stage, and invalid/non-string/empty ids, in parser/validation with a specific error; unknown but syntactically valid ids are runtime errors, not a reason an otherwise portable template cannot load. `auto` with no target has no effect. Existing defaults remain unchanged. Terminal stages never auto-dispatch, including a custom template naming an agent on done; terminal chat remains usable. Document this deliberate boundary.

An explicit target override is validated before a lifecycle mutation; bad id/missing definition returns a refusal without moving. A configured default that is missing or unavailable does not trap a ticket in a stage: move it and return an actionable dispatch failure. Harness/auth/model capability checks remain the existing broker's responsibility; never silently choose a different agent/model.

### 2. Actor and recipient are separate

Change the lifecycle CLI `--agent <id>` meaning on `start` to dispatch recipient, and add `--by <name>` for audit attribution on all moving/flag verbs and plan create/version. Remove `--agent` as an actor alias from all lifecycle verbs and plan commands; `start --agent` is the only lifecycle recipient option. `assign --agent`, `log --agent` and `track-session --agent` retain their existing separate meanings. Backward compatibility is waived for this v2 change. Internally use `actor?: string`, `dispatchAgent?: string`, and `callerSession?: ResolvedSession`; no ambiguous `agent` field crosses into `moveTicket`. Migrate all internal callers/tests. Dashboard JSON `agent` becomes dispatch recipient on start only; use a separate `by` field for audit attribution (default human). Reject recipient overrides on other verb endpoints rather than silently ignoring them. Manual dispatch uses its own `agentId` field.

`moveTicket` never calls resolveVerbActor/resolveSessionEngagement; callers pass actor (default human for programmatic calls) and the verified optional callerSession. Resolve CLI actor/caller once before mutation from the real runtime identity; only STRONG/EXPLICIT identities may switch an engagement. WEAK transcript/cwd guesses may not bind a session, even when the ticket id is explicit. Dashboard calls supply actor=human and no callerSession; never infer its launching terminal as the caller. `--by` is attribution only, not a session id.

After a successful stage change, update only an existing open engagement of a registered, active, non-ACP calling session through `switchSessionStage`, using the explicit ticket id and new stage. No session/engagement is created when absent or closed; repeated same target/stage is a no-op. A CLI invoked from hosted ACP must not split/replace the broker's per-turn engagement. Session-update failure is a warning after the stage change, never a reason to rerun the mutation. File-only operations/flags leave engagement stage unchanged. Apply to plan create, plan version and creation as well as moveTicket.

### 3. Stage entry identity and serialization

Every successful live `created` or stage-changing `moved` event receives one UUID generated once at the mutation boundary: this is BOTH `event_id` and `details.stageEntryId`. A zero-row live insert is an explicit failure, never silent INSERT OR IGNORE success. Record the resolved dispatch policy and any validated start override in that event as `dispatchTarget`/`dispatchRole`/`dispatchAuto`; the broker validates automatic requests against these recorded values, not client claims. Expose it as the current entry identity; do not use timestamp or stage name alone (reopen/re-entry and same-second events must differ). Extend event helpers/writer input to allow a known event id and to return a write outcome while retaining best-effort behavior for existing non-dispatch callers. For latest stage identity use insertion order as tie-breaker (`at DESC, rowid DESC`) and test same-second transitions.

Use two phases in `src/lifecycle/stage-entry.ts`: `recordStageEntryLocked` records the event/immutable dispatch intent inside the mutation lock after the ticket write; `completeStageEntry` updates the caller engagement and attempts delivery after releasing that lock. Call it from moveTicket's normal/reopen/drop paths, plan version's real stage move, and both creation paths after scaffolds/ticket are complete. File-only approve/plan/version-in-planning, flag/unflag, retemplate, direct reads, migrations and scans never generate an automatic dispatch. Drop/done invalidate older queued requests but do not launch a target. On any stage-entry notification the broker persists superseded for prior unstarted requests immediately, including terminal moves, without materializing/auto-driving ordinary queues. If that notification cannot reach the broker, the next receipt read or queue drive reconciles and persists superseded before reporting queued; it never cancels in-flight work. Reopen uses its destination stage's policy. New uses its initial stage's policy.

Serialize lifecycle read/check/write/event steps across CLI and dashboard with a shared per-ticket lock in `src/utils/ticket-mutation-lock.ts` (exclusive filesystem create, owner pid + process start identity + random token, bounded wait, release in finally only if token matches; recover only an absent pid (ESRCH) or a verified pid-reuse start-identity mismatch; EPERM/unknown identity is not proof of death. Never copy ticket-ids.ts's 30-second mtime eviction or evict a live owner on elapsed time). Store locks beneath `<syntaurRoot>/runtime/locks`, keyed by hash of canonical ticket path. Add the helper to plan creation/versioning, flags and unapprove as well, with an internal already-locked mutation helper to prevent recursive lock acquisition. In runPlanVersion, plan-block/approval clearing, status write and entry event must be a SINGLE lock section, not two writes around applyPlanVersionStageMove; plan file creation/version allocation occurs in that same operation. Retemplate also takes this lock, without dispatching. Existing plan-create --force remains scaffold overwrite semantics, not a new implicit gate bypass. Keep network calls, engagement token reads and broker work outside the lock. The second of two simultaneous start calls re-reads status and refuses, generating no extra entry or dispatch. Creation already has id-allocation locking; acquire the ticket lock once its path exists.

Filesystem writes and events DB are not one transaction. If the file commit succeeds but recording its entry fails, return `stageChanged:true, dispatch:{state:'failed',error:...}`; print both facts. Never auto-dispatch from an unrecorded entry. The current handoff descriptor verifies latest event's destination against actual status; when no matching event exists, expose a manual-only fallback token `unrecorded~<status>~<sha256>` whose digest covers current status/template and latest available event identity. Reject this non-UUID token for automatic source with 409. Do not auto-recover historical stage entries or infer a transition from a watcher. Manual dispatch remains available after operator inspection. This explicitly favors a visible missed dispatch over duplicate automatic work after a crash between file and event persistence.

## MAJOR

None — but two things worth eyeballing before merge because they were assumptions the prior review made:

1. The cross-path collation claim ("aligned collation between the SQL and merge paths") is only approximately true. `src/utils/session-sort.ts` routes `assignment_asc`/`agent_asc` through the merge path only for usage/duration sorts; for those, `compareKeys` (api-agent-sessions.ts:333, :338) uses `String.prototype.localeCompare` with default sensitivity, while the SQL ordering uses `COLLATE NOCASE`. For sessions whose `agent`/`assignment_slug` differ only by diacritics (e.g. `café` vs `cafe`), `localeCompare` can rank them differently from `COLLATE NOCASE`. Net effect: switching a user between, say, `started_desc` (SQL) and `spend_desc` (merge) with the *same* rows could reorder rows that tie on the primary key — but since spend_desc only ties when cost is equal and tie-breaks on `started` then sessionId, the divergence only surfaces for *rows that tie on cost and started*, which is rare. **Not major; flag it.** Fix if you care: pass `{ sensitivity: 'base' }` (or use `Intl.Collator`) to `localeCompare` so it matches NOCASE's case+accent folding.

2. Per-bucket count accuracy under cross-DST date ranges. `dashboard/src/hooks/useProjects.ts:816` now anchors `tzOffset` on `startedFrom || startedTo`. If a user sets `startedFrom=2026-07-…` and `startedTo=2026-12-…` in a DST zone, the *To* boundary is computed with the *From* date's offset (`localDateToUtcBounds(startedTo, offsetMinutes, 'end')`). The Dec 31 23:59:59 local-to-UTC shift will be an hour off, so an 11pm-local session on the *to* date could be excluded by an hour. Minor in practice; manifests only at the ungrouped DST edge. Fix: compute one offset per date (`new Date(\`${startedFrom}T12:00:00\`)` and `new Date(\`${startedTo}T12:00:00\`)` separately), or send two offsets.

- **Per-request 3× redundant scans.** The `countFor` block (api-agent-sessions.ts:586) calls `pageSessions` up to three extra times per request, and each invocation independently re-runs `listSessionUsage()` + `listAllSessionIds()` + a full sort whenever `includesUsageOnlyRows(a)` is true (i.e. always for `'usage-only'`, and for `'all'` if you ever add it). Correctness is fine; the per-bucket counts are independent and consistent. But each call is O(N) in the session and usage tables, and the sort inside is wasted work since only `keys.length` is read. Fix when scaling matters: a single pass `buildSessionFilters` query that returns `assigned`, `unassigned`, and total tracked counts in one `SUM(CASE WHEN …)` query, plus a single orphan scan that applies `orphanPassesFilters` once and reuses the count. Don't bother yet.

- **`pageSessions`'s orphan sort waste in counts (same root cause).** `countFor('usage-only')` invokes the merge path which sorts the entire orphan set; only `totalCount` is consumed. Correctness-neutral, minor perf.

- **Unpaged path silently ignores `attribution`.** `api-agent-sessions.ts` `pageSizeRaw === undefined` branch (line 476) returns the full set via `listAllSessions` and `attachUsage(...{includeUsageOnly})`; the `attribution` query param is never consulted on that branch. No current dashboard consumer hits that branch while sending `attribution` (the page always sends a `pageSize`), so nothing breaks today — but a future API caller that sends `attribution=assigned` without `pageSize` will silently get the full `sessions` table. Fix worth a one-liner guard when you have time: reject or honor the param on the unpaged path, or document that `attribution` requires `pageSize`.

- **`AgentSessionsPage.tsx` default-change backward compatibility.** The page previously sent `includeUsageOnly: true`; it now defaults `attribution` to `'tracked'` (line 78) and sends no `includeUsageOnly`. A returning user whose mental model was "this page shows spend-only rows too" will see them vanish from the default view with no notice beyond the new dropdown. This matches the commit's stated intent and the legacy server fallback (an absent `attribution` plus `includeUsageOnly=0` resolves to `'tracked'`), so it is *intentional*, not a bug — but it is a behavior change a user could perceive as "lost rows." Mention in a CHANGELOG/release note.
